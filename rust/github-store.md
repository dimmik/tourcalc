# Хранилище туров в публичном репозитории GitHub, зашифрованное — план

*Записано 2026-11-11, по разговору. Начато 11.11 по слову владельца: шаги 1–5 — первый PR.*
Ветка — `beta/github-store` (от `prod`).

## Что решено

- **Альтернатива, а не зеркало:** третий вид хранилища рядом с памятью и Mongo,
  `StorageType=GitHub`. Mongo туда не копируется и основным не остаётся.
- **Пока только локально:** проверяем на своей машине (через туннель), не на бете и не на
  проде. Данные для начала — туры из файла-образца InMemory (`InMemoryFileName`), а не из
  Mongo; перенос из Mongo — позже, если понадобится.
- **Несохранённые правки ждут до 10 секунд** (`GitHubFlushSeconds=10`) — в памяти сервера:
  читается всё из неё же, при обычной остановке недописанное дописывается, при падении
  процесса — теряется.
- **История репозитория пока не сжимается** — это следующий шаг, отдельно.
- **Память — с потолком, остальное — на диске** (из разговора 11.11): версии в памяти не
  держатся, туры, которых давно не трогали, вытесняются в кэш на диске.
- **Состояние хранилища видно в интерфейсе** — внизу страницы Help, рядом с «This build».
- **Открыто — репозиторий для данных и токен к нему:** владелец делает отдельно (11.11
  вечером). Нынешний токен — только на `dimmik/tourcalc`, на репозиторий данных нужен свой.

## Как устроено

Сервер держит хранилище за трейтами `TourStore` (`tc-server/src/store.rs`) и
`SubscriptionStore` (`subscriptions.rs`); GitHub — их третья реализация, рядом с
`InMemoryStore` и `MongoStore`, остальной сервер её не замечает.

1. **Отдельный публичный репозиторий только под данные** (например
   `dimmik/tourcalc-data`) — не репозиторий кода: каждый коммит данных запускал бы
   сборки. Токен — fine-grained, `Contents: write` только на него.
2. **Память и диск — основное, GitHub догоняет.** Чтение — из памяти, а чего там нет — из
   кэша на диске (п. 3), к GitHub на чтение сервер ходит только при старте. Запись меняет
   память сразу и помечает тур изменённым; раз в `GitHubFlushSeconds` все изменённые уходят **одним
   коммитом** через Git Data API: ссылка ветки → дерево (содержимое прямо в дереве) →
   коммит → сдвиг ветки, только если она не сдвинулась (иначе перечитать и повторить).
   ≈ 4 запроса на пачку при лимите 5000 в час. При остановке (SIGTERM) — дописать.
3. **Память с потолком, кэш на диске.** Замер на образце «Поход Урал» (64 траты): JSON
   ≈ 290 КБ (тур хранит и посчитанные долги), сжатый ≈ 8,5 КБ. Каждое сохранение оставляет
   версию — у живого тура их сотни, и в памяти они за год стали бы гигабайтами. Поэтому:
   - **версии в памяти — только списком** (id, тур, время, комментарий, ≈ 100 байт);
     сама версия читается с диска, когда её открыли;
   - **кэш на диске** (`GitHubCacheDir`) — те же зашифрованные файлы, что в репозитории.
     При старте — сверка по SHA блоба git с деревом репозитория: скачивается только
     изменившееся, а не всё; так и старт быстрый;
   - **в памяти — горячие туры, до `GitHubMemoryMB`** (по умолчанию 32 — около 50 туров на 65 трат: такой тур ≈ 0,65 МБ в памяти, замер 11.11): давно не
     тронутый вытесняется в кэш и читается обратно при обращении (расшифровать и
     распаковать — миллисекунды). Вытесняется и тур, ещё не записанный на GitHub: он уже в кэше на диске, а в репозиторий уйдёт из списка изменённых;
   - **раз в несколько минут — строка в лог**: сколько туров в памяти и сколько они
     занимают, — чтобы видеть, верен ли потолок.
4. **Имена файлов ничего не говорят:** тур — `t/<HMAC(ключ, id тура)>`, его версии —
   `v/<HMAC(id тура)>/<HMAC(id версии)>`, push-подписки — один файл `s`. Иначе id из
   ссылок `/goto/…` сопоставлялись бы с файлами.
5. **Шифрование:** JSON тура сжимается и шифруется XChaCha20-Poly1305 (крейт
   `chacha20poly1305`, чистый Rust — без C, как вся сборка). Ключ — 32 байта,
   `GitHubStoreKey` (base64). Nonce своя на каждую запись; путь файла — в AAD, чтобы файл
   нельзя было подменить другим. Заголовок: `TCE1`, номер ключа (для будущей смены),
   nonce.
6. **Настройки:** `StorageType=GitHub`, `GitHubRepo` (`owner/name`), `GitHubBranch`,
   `GitHubToken`, `GitHubStoreKey`, `GitHubFlushSeconds` (10), `GitHubCacheDir`,
   `GitHubMemoryMB` (32). Сборка — `--features
   github`, как `mongo`: исходящий HTTPS тянет TLS (`reqwest` с rustls уже есть у push).
7. **Начальные данные:** разовая команда сервера — туры (и их версии) из файла-образца
   InMemory записать в репозиторий. Mongo ↔ GitHub — потом.
8. **Тесты:** GitHub в тестах — поддельное удалённое хранилище в памяти. Шифрование туда и
   обратно, отказ на чужом ключе и на подменённом пути; пачка правок — один коммит;
   ветку сдвинули — перечитать и повторить; дозапись при остановке; вытеснение в кэш и
   чтение обратно; старт с кэшем скачивает только изменившееся. Живой репозиторий —
   по переменной, как `TC_TEST_MONGO`, иначе тест пропускается (и это сказано в выводе).
9. **Состояние хранилища на странице Help** — внизу, рядом с «This build» (свежесть
   клиента и сервера, `version::AboutBuild`). Сервер отвечает на новый
   `GET /api/Info/storage`, клиент спрашивает его вместе с `/api/Info/version` и по кнопке
   «обновить»:
   - **всем:** вид хранилища и что это значит для данных — «в памяти: пропадёт при
     перезапуске», «MongoDB», «GitHub, зашифровано»; для GitHub — **всё ли записано**:
     «записано, 12 с назад» или «ждёт записи: 3 тура, следующая через 7 с», и последняя
     ошибка записи, если была («GitHub ответил 403 в 11:20, повтор через 30 с»);
   - **администратору** (вход мастер-ключом) — ещё: репозиторий и ветка, последний коммит
     ссылкой, туров в памяти / в кэше, занято памяти из `GitHubMemoryMB`, размер кэша на
     диске, вытеснений с запуска, когда был старт и сколько скачал. Остальным это не
     показывается: имя репозитория с данными — не секрет, но и незачем.
   - Тексты — на двух языках, справка — строкой о том, что это за блок.
10. **Живая проверка:** тестовый публичный репозиторий, локальный сервер через туннель —
   траты, перезапуск, всё на месте; репозиторий глазами постороннего.

## Что видно постороннему и чем это грозит

- **Видно:** сколько туров, их примерный размер, когда и как часто их правят (время
  коммитов). Размер можно выровнять ступеньками, время — нет.
- **История вечная:** публичный репозиторий могли склонировать, так что утечка ключа
  раскрывает всё, что когда-либо было записано, и это уже не стереть. Ключ — как пароль от
  всего.
- **Потеря ключа — потеря данных:** копия ключа — вне сервера.
- **Рост репозитория:** каждое сохранение — тур целиком, и шифрованное git не сжимает.
  ≈ 100 сохранений в день × ≈ 6 КБ = ≈ 0,6 МБ в день, ≈ 200 МБ в год. Лечится сжатием
  истории (ветка без истории + force push) — следующий шаг.
- **Сервер один:** двое на одном репозитории спорят за ветку. Сдвиг ветки с проверкой
  данные не теряет, но работа вдвоём не задумана.

## Шаги

| шаг | что | оценка (Opus 5.5) |
|---|---|---|
| 1 | формат файла и шифрование, тесты | ≈ 10 мин |
| 2 | клиент GitHub: прочитать всё; записать пачку со сдвигом ветки по проверке; поддельный для тестов | ≈ 15 мин |
| 3 | `GitHubStore`: память с потолком, кэш на диске со сверкой по SHA, список версий, изменённые, запись в фоне, дозапись при остановке; туры, версии, подписки | ≈ 25 мин |
| 4 | настройки, `main.rs`, флаг сборки, Readme и GUIDE | ≈ 8 мин |
| 5 | состояние хранилища: `/api/Info/storage` (всем / администратору), блок на Help, тексты на двух языках, журнал изменений; снимки 420 и 1100 | ≈ 15 мин |
| 6 | туры из файла-образца InMemory → репозиторий | ≈ 8 мин |
| 7 | живая проверка (нужны репозиторий и токен) | ≈ 10 мин |

Итого ≈ 1 ч 30 мин; PR — два: шаги 1–5, затем 6–7. Шаги 1–6 делаются без репозитория и
токена (на поддельном GitHub), шаг 7 — только с ними. Блок на Help — визуальный, вероятен
раунд правок.

**Следующим шагом, отдельно:** сжатие истории; перенос Mongo ↔ GitHub; смена ключа.
