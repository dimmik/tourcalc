# Tourcalc на Rust — план

Учебный проект: переписать Tourcalc (новый UI + сервер) на Rust так, чтобы получившийся
код можно было читать как учебник — «вот здесь владение, вот здесь заимствование, вот
почему компилятор не пустил». Без `unsafe`, без C-подобного кода в растовой обёртке.

Побочные цели — меньше весить и меньше есть памяти — реальны, но вторичны: если бы
задача была только в этом, дешевле было бы дочистить .NET (см. §12).

---

## 1. Что мы знаем про сегодняшнее приложение

Всё измерено, не оценено:

| | |
|---|---|
| Клиент, `_framework` под brotli | **4.05 МБ** (после удаления AntDesign; было 4.91) |
| Серверные DLL в публикации | **11.2 МБ** |
| Память серверного процесса | **~308 МБ** |
| Полный расчёт по всем турам (`/api/tour/all/suggested`) | **60 мс** |
| Отдача статики | 3.7 мс |
| Старт до первого ответа | 1.8 с |

Размер кода, который предстоит перенести:

| проект | файлов | строк | что это |
|---|---|---|---|
| `TCalcCore` | 38 | 3 159 | домен, калькулятор, сетевой слой, очередь операций |

сам по себе наследие. Переносим Full и Mini — они делят одну разметку и один CSS.

## 2. Что именно даст Rust, а что нет

Честно по пунктам, потому что от этого зависит, стоит ли овчинка выделки.

**Размер клиента — да, и сильно.** Сейчас браузер качает *рантайм* .NET: `dotnet.native.wasm`
(2.9 МБ), `System.Private.CoreLib` (2.1 МБ), сборщик мусора, JIT-интерпретатор — и уже
поверх этого твой код (`TCBlazor.Client.wasm`, 584 КБ). У Rust рантайма в этом смысле нет:
в `.wasm` попадает только то, что реально вызывается, плюс аллокатор на пару килобайт.
*Оценка:* сотни килобайт вместо мегабайтов. Проверяется в §11, фаза 0 — до того, как
писать что-то всерьёз.

**Память сервера — да.** 308 МБ у процесса, который считает суммы для десятка человек, —
это GC, который просто не торопится отдавать страницы. Rust отдаёт память в момент, когда
владелец выходит из области видимости. *Оценка:* 10–30 МБ.

**Скорость расчёта — почти нет.** 60 мс уже быстро, и большая часть этого — не арифметика,
а JSON и `Newtonsoft`. Rust ускорит, но задачи такой нет.

Любопытно другое: этого JSON в коде больше, чем кажется. Тур сериализуется в строку и
разбирается обратно **просто чтобы получить его копию** — в конструкторе `TourCalculator`
(`TourCalculator.cs:19`), в `InMemoryTourStorage.GetTour` (`:35`), в `Tour.Clone()` и в
`AbstractItem.SafeClone`. Причина везде одна: «пусть у меня будет свой экземпляр, чтобы
никто ничего не испортил». В Rust эти клоны не оптимизируются, а **исчезают** — потому что
право изменить объект выражается типом, а не копией (§5.1, §5.2).

**Скорость UI — вероятно да, но не в этом дело.** Blazor WASM гоняет диффы через
интерпретатор IL; Leptos с мелкозернистой реактивностью вообще не строит виртуальный DOM.
На туре в 64 траты разницы никто не заметит.

**Чего Rust не даст:** ничего не изменится в том, как приложение устроено логически.
Переписывание — это не рефакторинг архитектуры. Если что-то путано сейчас, оно будет
путано и на Rust, только компилятор будет об этом громче ругаться.

## 3. Раскладка: cargo workspace

```
tourcalc/
├── Cargo.toml              # [workspace] members = [...]
├── crates/
│   ├── tc-core/            # домен + арифметика. Никаких зависимостей, кроме serde.
│   ├── tc-api/             # типы запросов/ответов, общие для клиента и сервера
│   ├── tc-server/          # axum: API, /t, бот, хранилище
│   └── tc-web/             # leptos: Full и Mini, wasm32-unknown-unknown
└── tests/
    └── golden/             # JSON-фикстуры, снятые с работающего C#
```

Главное здесь — `tc-core`. Он собирается **и** в нативный сервер, **и** в wasm-клиент, и
это не оптимизация, а условие задачи: если офлайн-клиент считает балансы сам, а сервер
считает их же для API, текстовых страниц и бота, то реализация обязана быть одна. Ровно
это и есть причина, по которой «переписать только сервер на Rust» — плохая идея: алгоритм
удвоится, и две копии обязаны совпадать до копейки навсегда.

`tc-core` не знает про HTTP, про базу, про браузер и про время. Он берёт данные и
возвращает данные. Такой крейт:

* компилируется за секунды и тестируется без всякого окружения;
* переносится на любой target, включая `wasm32`;
* не тянет `tokio`, а значит не тянет пол-экосистемы в клиентский бандл.

Правило, которое стоит держать: **зависимость, попавшая в `tc-core`, попадает в браузер.**

## 4. Модель данных: из C# в Rust

Это первое место, где Rust виден невооружённым глазом, и первое, где стоит сознательно
*не* переносить С#-структуру один в один.

### 4.1. Идентификаторы

Сейчас всё — `string`. `Spending.FromGuid`, `Person.ParentId`, `Tour.Id`, `Person.GroupId`,
`Person.FamilyId` — семь разных смыслов в одном типе, и перепутать их может только
компилятор, который этого не делает.

```rust
/// Обёртка вокруг строки, которую нельзя перепутать с другой обёрткой вокруг строки.
/// Никаких накладных расходов в рантайме: после компиляции это просто String.
#[derive(Debug, Clone, PartialEq, Eq, Hash, serde::Serialize, serde::Deserialize)]
#[serde(transparent)]
pub struct PersonId(String);

#[derive(Debug, Clone, PartialEq, Eq, Hash, serde::Serialize, serde::Deserialize)]
#[serde(transparent)]
pub struct TourId(String);
```

`#[serde(transparent)]` — чтобы в JSON это осталось обычной строкой и старые данные
читались как есть. `PersonId` в функцию, ожидающую `TourId`, не пролезет: ошибка
компиляции, а не пустой результат в проде.

### 4.2. Деньги

`long AmountInCents` — уже правильно (копейки в целых). Закрепим:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Default)]
#[derive(serde::Serialize, serde::Deserialize)]
#[serde(transparent)]
pub struct Cents(pub i64);

impl std::ops::Add for Cents { /* ... */ }
impl std::ops::Sub for Cents { /* ... */ }
// Умножения Cents * Cents намеренно нет: у произведения денег на деньги нет смысла.
```

`Copy` здесь уместен: восемь байт, копировать дешевле, чем заимствовать. Это первый
случай, где придётся решать «`Copy` или нет», и правило простое — маленькое и без
владения чем-либо в куче.

Конвертацию валют в C# делает `AmountInCurrentCurrency` через `double` и `Math.Round`.
В Rust считаем в `i128` и округляем явно — плавающей точки в деньгах быть не должно:

```rust
pub fn to_currency(amount: Cents, from: &Currency, to: &Currency) -> Cents {
    if from.id == to.id { return amount; }
    let num = amount.0 as i128 * from.rate as i128;
    let den = to.rate as i128;
    Cents(((num + den / 2) / den) as i64)   // округление к ближайшему
}
```

### 4.3. Как делится трата — главный выигрыш от enum

В C# это четыре независимых поля: `ToAll`, `ToGuid`, `Weighted`, `IsPartialWeighted`.
Комбинаций 2×2×2 = восемь, осмысленных — три. Остальные пять существуют и требуют, чтобы
каждый читающий держал в голове, какие сочетания «не бывают».

```rust
/// Три способа поделить трату — и ни одного четвёртого.
/// Невыразимое состояние не нужно проверять: его нельзя построить.
#[derive(Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize)]
pub enum Split {
    /// на всех участников тура, по весам
    Everyone,
    /// на перечисленных, поровну
    Equally(Vec<PersonId>),
    /// на перечисленных, по их весам
    ByWeight(Vec<PersonId>),
}
```

Компилятор теперь требует разобрать все три ветки в `match` — забыть третью нельзя.
Это и есть то, ради чего в Rust вообще есть enum: не «перечисление констант», а
«одно из, с данными внутри».

Ровно так же:

```rust
pub enum Kind {
    Real,                       // обычная трата
    Draft { counted: bool },    // IsDryRun + IncludeDryRunInCalc
    Planned,                    // предложенный перевод, не введённый человеком
}
```

`Option<PersonId>` вместо `string ParentId = null` — «нет родителя» становится значением
типа, а не соглашением, и `null`-а в Rust просто нет.

### 4.4. Совместимость с существующими данными

**Это ограничение, а не пожелание.** В Mongo лежат туры, в браузерах — `localStorage` с
турами и очередью операций. Новый код обязан читать старый JSON.

Поэтому у каждого нового типа — свой `Serialize`/`Deserialize`, приводящий к старой форме:

```rust
// на проводе по-прежнему {"ToAll": true} либо {"ToGuid": [...], "IsPartialWeighted": true}
impl Serialize for Split { /* пишем в старом виде */ }
impl<'de> Deserialize<'de> for Split { /* читаем старый вид, собираем enum */ }
```

Это скучная часть работы, и её нельзя пропустить. Зато она отлично проверяется:
взять дамп реального тура, прочитать, записать обратно, сравнить с исходником побайтово
(§10).

## 5. Владение и заимствование — на конкретных местах этого проекта

Ради этого раздела всё и затевается. Ниже — реальные места, где Rust заставит принять
решение, которое в C# принималось само (обычно в сторону «скопируем на всякий случай»).

### 5.1. Калькулятор, который не клонирует

Сегодня:

```csharp
public TourCalculator(Tour tour, Currency currency) {
    // clone
    CurrentTour = JsonConvert.DeserializeObject<Tour>(JsonConvert.SerializeObject(tour));
    ...
}
```

Тур сериализуется в строку JSON и разбирается обратно — чтобы калькулятор мог свободно
мутировать его, не трогая объект вызывающего. Это единственная причина.

Клон делается один раз на конструирование, не на каждый пересчёт: цикл подбора платежей
вызывает `Calculate` на уже построенном калькуляторе. Но конструируется калькулятор в
десяти местах — на запрос к API, на отрисовку страницы тура, на каждое сообщение боту, на
каждую текстовую страницу; `Tour.PrepareForStoring` строит его дважды за одно сохранение,
а `/api/tour/all/suggested` — по разу на тур.

(Не путать с тем клоном, который мы уже чинили: `Tour.Currency` делал JSON-круг на каждое
чтение свойства, то есть тысячи раз за рендер. Его заменили на сборку копии руками. Этот,
в конструкторе, остался.)

В Rust вопрос «а не испортит ли функция мои данные» решается сигнатурой:

```rust
/// Берёт тур взаймы (только на чтение) и возвращает новый, свой результат.
/// `&Tour` — заимствование: калькулятор не владеет туром и не может его изменить,
/// а вызывающий это видит по типу и не обязан ничего копировать.
pub fn calculate(tour: &Tour, opts: CalcOptions) -> Balances { ... }

/// Результат — отдельный тип, а не мутированная копия входа.
pub struct Balances {
    pub per_person: Vec<PersonBalance>,
    pub rounding: Vec<RoundingNote>,
}
```

Клон исчезает не потому, что мы его «оптимизировали», а потому что он был обходным путём
для проблемы, которой в Rust нет. Это, пожалуй, самый наглядный пример на весь проект:
**владение — это не про производительность, это про то, кто имеет право изменить объект.**

Подбор платежей, который в C# мутирует `CurrentTour.Spendings` в цикле, становится
чистой функцией с накоплением:

```rust
pub fn suggest_settlement(tour: &Tour) -> Result<Vec<Transfer>, CalcError> {
    let mut transfers = Vec::new();
    let mut balances = calculate(tour, CalcOptions::with_planned(&transfers));
    for _ in 0..MAX_ITERATIONS {
        let Some((debtor, creditor)) = pick_pair(&balances) else { return Ok(transfers) };
        transfers.push(Transfer::between(debtor, creditor, /* ... */));
        balances = calculate(tour, CalcOptions::with_planned(&transfers));
    }
    Err(CalcError::DidNotConverge { max: MAX_ITERATIONS })
}
```

Заодно `throw new Exception("Max of 500 iterations exceeded")` превращается в типизированную
ошибку, которую вызывающий обязан обработать (§6).

### 5.2. Хранилище: `Arc` вместо клона на каждом чтении

Сегодня `InMemoryTourStorage.GetTour` возвращает клон — опять же чтобы никто не испортил
общее состояние. В Rust у этого есть точное выражение:

```rust
use std::sync::{Arc, RwLock};

pub struct InMemoryStore {
    // RwLock: много читателей одновременно, писатель — один и эксклюзивно.
    // Arc<Tour>: сам тур не копируется при чтении, копируется только счётчик ссылок.
    tours: RwLock<HashMap<TourId, Arc<Tour>>>,
}

impl InMemoryStore {
    pub fn get(&self, id: &TourId) -> Option<Arc<Tour>> {
        self.tours.read().unwrap().get(id).cloned()   // .cloned() клонирует Arc, не Tour
    }

    pub fn update(&self, id: &TourId, f: impl FnOnce(&mut Tour)) {
        let mut map = self.tours.write().unwrap();
        if let Some(arc) = map.get_mut(id) {
            // copy-on-write: если на тур больше никто не смотрит — меняем на месте,
            // если смотрит — сначала делаем свою копию. Ровно один клон, и только когда нужен.
            f(Arc::make_mut(arc));
        }
    }
}
```

Здесь видно три вещи разом: разделяемое владение (`Arc`), синхронизация доступа
(`RwLock`) и copy-on-write (`Arc::make_mut`). В C# всё это было спрятано за «вернём копию,
так спокойнее».

### 5.3. `Arc` на сервере, `Rc` в браузере

`Arc` — атомарный счётчик ссылок, `Rc` — обычный. Разница в цене атомарной операции, и
компилятор не даст отправить `Rc` в другой поток: у него нет `Send`. В браузере потока
одного, поэтому в `tc-web` — `Rc`, на сервере — `Arc`. Это первая встреча с
«маркерными» трейтами `Send`/`Sync`, и она произойдёт сама, без специальных усилий.

### 5.4. UI: почему `Rc<RefCell<T>>` встречается, но его не должно быть много

Классическая ловушка новичка — обмазать всё состояние в `Rc<RefCell<...>>` и получить
панику «already borrowed» в рантайме. В Leptos для состояния есть сигналы, и они этот
случай закрывают:

```rust
let (tour, set_tour) = create_signal(None::<Arc<Tour>>);

// Обработчик события владеет только копией сеттера — это дёшево и не держит сам тур.
let on_add = move |sp: Spending| {
    set_tour.update(|t| { if let Some(t) = t { Arc::make_mut(t).spendings.push(sp) } });
};
```

Правило, которое стоит записать в самом коде: `RefCell` — это перенос проверки
заимствования из компиляции в рантайм. Иногда нужен (интероп с JS-колбэками), но каждое
его появление стоит комментария «почему здесь нельзя иначе».

### 5.5. Времена жизни (`'a`) — где они реально появятся

Не везде. В приложении такого рода лайфтаймы возникают в трёх местах:

1. Итераторы, заимствующие тур: `fn debtors(&self) -> impl Iterator<Item = &Person> + '_`
   — «этот итератор живёт не дольше, чем тур, по которому он идёт».
2. Разбор входных данных без копирования: `&'a str` вместо `String` там, где строка
   только читается (например, парсинг команд бота).
3. Обобщённые функции над данными тура.

Всё остальное обходится владеющими типами. Если лайфтаймы полезли в структуры данных —
это почти всегда сигнал, что нужен `Arc`, а не `&'a`.

## 6. Ошибки

Исключений нет. Вместо них `Result<T, E>` и оператор `?`, который пробрасывает ошибку
наверх, если она есть.

```rust
#[derive(Debug, thiserror::Error)]
pub enum CalcError {
    #[error("подбор платежей не сошёлся за {max} итераций")]
    DidNotConverge { max: usize },
    #[error("трата {spending} ссылается на неизвестного участника {person}")]
    UnknownPerson { spending: SpendingId, person: PersonId },
}
```

В `tc-core` — свои перечисляемые ошибки (`thiserror`), потому что вызывающий должен уметь
их различать. В `tc-server`, где ошибка чаще всего просто превращается в HTTP-код,
достаточно `anyhow`. Это стандартное разделение, и его полезно увидеть в одном проекте.

Отдельно: в C# `Person.ParentId` может указывать на несуществующего человека, и код
это молча переживает (`?? "n/a"`). В Rust такие места придётся назвать явно — либо
`Option`, либо ошибка валидации при загрузке. Скорее второе: невалидный тур лучше
отвергнуть на входе, чем таскать «n/a» по всему UI.

## 7. Клиент: выбор фреймворка

| | как устроен | размер | как ощущается после Blazor |
|---|---|---|---|
| **Leptos** (CSR) | мелкозернистая реактивность, без VDOM | наименьший | сигналы вместо `StateHasChanged`, поначалу непривычно |
| **Dioxus** | VDOM, компоненты и пропсы | средний | ближе всего к Blazor/React |
| **Yew** | VDOM, старше и стабильнее | средний | много boilerplate |
| **Sycamore** | как Leptos | наименьший | меньше экосистемы |
| без фреймворка | руками через `web-sys` | минимальный | для приложения с четырьмя вкладками — мазохизм |

**Рекомендация: Leptos, режим CSR** (не SSR — нам нужен офлайн, страница должна работать
без сервера). Причины: размер как основной критерий; реактивность без VDOM хорошо ложится
на «пересчитать балансы при изменении траты»; и она заставит разобраться с тем, как в Rust
живут замыкания и `move` — а это ровно то, чему стоит научиться.

Оговорка: это **решение фазы 0**, а не догма. Сначала спайк, потом выбор (§11).

Разметка и CSS переносятся почти как есть — `newui.css` и `mini.css` написаны под обычные
классы, без привязки к Blazor. Это, пожалуй, самая приятная часть переезда: три с
половиной тысячи строк CSS работают дальше.

## 8. Офлайн

Устройство остаётся тем же, что сейчас, и это осознанно — оно работает:

* **Service worker** кэширует оболочку и ассеты. Пишется на JS (у SW нет разумного
  растового пути), файл переезжает почти без изменений.
* **Очередь операций.** Сейчас это `SerializableTourOperation` — имя операции, id, JSON
  элемента. В Rust это просится в enum:

```rust
#[derive(serde::Serialize, serde::Deserialize)]
#[serde(tag = "OperationName")]     // сохраняем формат, лежащий у людей в localStorage
pub enum Operation {
    AddSpending { item: Spending },
    UpdateSpending { id: SpendingId, item: Spending },
    DeleteSpending { id: SpendingId },
    AddPerson { item: Person },
    UpdatePerson { id: PersonId, item: Person },
    DeletePerson { id: PersonId },
    ChangeName { name: String },
    // ...
}
```

  `match` по этому enum заменит `switch` со строками — и компилятор будет ругаться, если
  забыть ветку при добавлении операции. Сейчас забытая ветка — это тихий `default`.

* **Хранилище в браузере.** `localStorage` через `gloo-storage` (просто) или IndexedDB
  через `idb` (правильнее для больших туров). Начать с `localStorage`, потому что формат
  ключей уже есть и данные должны прочитаться.

## 9. Сервер

| сейчас | станет | замечание |
|---|---|---|
| ASP.NET Core MVC | `axum` + `tokio` | роуты как функции, middleware как `tower`-слои |
| `Newtonsoft.Json` | `serde_json` | минус ~700 КБ и минус `System.Private.Xml` (1.3 МБ) |
| `MongoDB.Driver` | крейт `mongodb` | официальный, асинхронный |
| `BouncyCastle` (2.4 МБ) ради `SecureRandom` и одной `BigInteger` | `rand` + `p256` | ES256 для JWT: `jsonwebtoken` или `p256` напрямую |
| `Microsoft.IdentityModel.Tokens` | `jsonwebtoken` | тот же ES256, тот же формат токена |
| Razor Pages для `/t` | `maud` или `askama` | `maud` — разметка прямо в Rust, с проверкой на компиляции |
| `Telegram.Bot` | `teloxide` или просто `reqwest` | логика бота уже отделена от транспорта — переносится почти механически |

Формат JWT и `AccessCodeMD5` остаются прежними: иначе у всех разом отвалятся сохранённые
ссылки-логины.

Про бота стоит сказать отдельно: `TourcalcBot.cs` написан так, что не знает про Telegram
вообще — принимает сообщение, возвращает ответ. Это ровно та форма, которая переносится
на другой язык без сюрпризов, и 115 существующих тестов проверяют именно её.

## 10. Тесты: как не переписать арифметику с ошибкой

Это самая важная часть плана, и её нельзя делать в конце.

**Золотые файлы.** Прежде чем писать растовый калькулятор, снять с работающего C# набор
пар «вход → выход»:

```
tests/golden/
  ural-2021.tour.json          # вход: реальный тур из inmemory-tours.json
  ural-2021.calculated.json    # выход Calculate()
  ural-2021.suggested.json     # выход SuggestFinalPayments()
  multicurrency.tour.json
  ...
```

Снимаются они маленькой утилитой на C#, один раз. Дальше растовый тест читает вход,
считает и сравнивает с эталоном — до копейки. Особенно важны туры с ошибками округления:
логика `DealWithRoundErrors` и «Distribution Rounding Error» неочевидна, и повторить её
по памяти невозможно — только по эталону.

**Тесты сериализации.** Прочитать реальный тур, записать обратно, сравнить с исходным
JSON. Это ловит расхождения формата до того, как они попадут в чью-то базу.

**Property-тесты** (`proptest`) — там, где есть инвариант, а не конкретный ответ:
сумма всех долгов после расчёта равна нулю; подбор платежей всегда сходится; сумма
переводов равна сумме долгов. На случайных турах это найдёт то, чего не найдут примеры.

**Порт существующих тестов бота.** 1 433 строки, почти все — про разбор команд и суммы.
Переносятся прямо.

## 11. Порядок работ

Каждая фаза заканчивается чем-то, что запускается и что можно посмотреть.

**Фаза 0 — спайк на два дня. Не пропускать.**
Пустое приложение на Leptos: заголовок, список из трёх строк, кнопка. Собрать
`--release`, сжать brotli, **измерить**. Если получится не «сотни килобайт», а пара
мегабайт — весь план надо пересматривать, и лучше узнать это сейчас. Заодно попробовать
Dioxus и сравнить и размер, и ощущение от кода.
*Результат: цифра и выбранный фреймворк.*

**Фаза 1 — `tc-core`.** Домен, конвертация валют, `calculate`, `suggest_settlement`,
сериализация в старый формат. Никакого HTTP, никакого UI. Золотые тесты зелёные.
*Это фаза, где происходит всё обучение владению — и она же самая интересная.*

**Фаза 2 — `tc-server`, только чтение.** `axum`, InMemory-хранилище, `GET /api/tour/{id}`
и список туров, JWT-проверка. Отдаёт то же, что нынешний сервер. Можно натравить
существующий Blazor-клиент на новый сервер — если работает, значит контракт соблюдён.
Это отличная проверка на честность.

**Фаза 3 — `tc-web`, только чтение.** Вкладка «Balance», список туров. Данные с сервера,
расчёт локально через `tc-core`. Уже видно настоящий размер бандла на настоящем коде.

**Фаза 4 — запись.** Диалоги траты и участника, очередь операций, синхронизация,
`PATCH`/`POST`/`DELETE` на сервере. Здесь будет больно с замыканиями и `move` — это
нормально и полезно.

**Фаза 5 — офлайн.** Service worker, `localStorage`, работа без сети, разрешение
конфликтов по `StateGUID`.

**Фаза 6 — остальное.** Mini (тот же код, другой CSS), Mongo, текстовые страницы `/t`,
бот, push-уведомления.

**Фаза 7 — параллельный прогон.** Оба сервера на одних данных, сравнение ответов на
одинаковых запросах. Только после этого что-то выключать.

## 12. Чего ожидать неприятного

Список нужен, чтобы не разочароваться на третий день.

* **Борьба с borrow checker в UI.** Замыкания-обработчики хотят захватить состояние, а
  состояние уже захвачено другим замыканием. Лечится сигналами и `move`-копиями дешёвых
  хендлов, но первые дни это раздражает больше всего.
* **Асинхронные трейты.** Стало сильно лучше (`async fn` в трейтах с Rust 1.75), но
  абстракция «хранилище» с асинхронными методами всё ещё требует аккуратности.
* **Граница с JS.** `wasm-bindgen` — единственное место, где `unsafe` существует, но он
  спрятан внутри библиотеки. Твоего `unsafe` в проекте быть не должно ни строчки; если
  захотелось — почти наверняка есть безопасный способ.
* **Даты.** `DateTime.Now` в C# — местное время без зоны, и в данных это уже так. `chrono`
  заставит выбрать между `NaiveDateTime` и `DateTime<Utc>`. Выбирать надо в сторону
  совместимости с тем, что лежит в базе, а не в сторону правильности.
* **Нет рефлексии.** Всё, что в C# делалось через сериализатор «сам разберётся», в Rust
  делается через `derive`. Это скорее плюс, но требует явности.
* **Экосистема Mongo** беднее .NET-овской, хотя официальный драйвер есть и работоспособен.
* **Время сборки.** Rust компилируется заметно дольше C#. `cargo check` в помощь.

И общее: **это переписывание работающего приложения ради нефункциональных свойств.**
Если бы целью был только размер, дешевле было бы доделать оставшееся на .NET —
Newtonsoft на `System.Text.Json` (это ещё ~2.5 МБ несжатого, потому что за ним уйдут
`System.Private.Xml` и `System.Data.Common`) и чистка серверных зависимостей
(BouncyCastle 2.4 МБ, LiteDB 1.4 МБ). Но цель здесь другая, и она названа честно.
