# Туркальк на Cloudflare Workers

Цель — уйти с дроплета DigitalOcean. Ветка кода `cf/worker-proto` (не `beta/*`: сборку беты не
трогает).

**Сейчас:** <https://tc-proto.dimmik-a.workers.dev> — весь туркальк: клиент, API, текстовые
страницы `/t`; туры — в GitHub, ветка `cf-worker`. Данные — копия туров прода из выгрузок 11.11
(`owsr6op-now.json`, `prod-two.json`: 3 тура и 123 версии), залитая через `/seed`; правки здесь
не трогают ни прод, ни бету.

## Как устроено

- **Клиент** (`rust/crates/tc-web/dist`) — статикой Workers: Cloudflare отдаёт файлы сам,
  Worker не запускается, бесплатно и вне лимита запросов. Неизвестный адрес (`/tour/...`,
  `/goto/...`) — `index.html`.
- **API, `/t`, `/service-worker.js`, `/seed`** идут в Worker (`run_worker_first`), а он — в
  один Durable Object `Store` (`id_from_name("server")`). **Объект и есть сервер:** в нём
  тот же роутер, что у `tc-server` (`api::routes`, `text::routes`), над тем же
  `InMemoryStore`. Запрос переводится в `http::Request` и обратно, axum отвечает как обычно.
- **Где туры — в GitHub, в своей ветке:** `cf-worker` репозитория `dimmik/tc-strg-test`
  (бета пишет в `master` того же репозитория; ветка на базу — так базы не мешают друг другу).
  Ключ шифрования свой (`STORE_KEY`), раскладка — как у хранилища сервера (`t/`, `v/`), так
  что ветку можно открыть и сервером с `StorageType=GitHub`. Ветки нет — объект делает её
  пустой, с одним README, не от `master`: чужие туры в базу не попадают.
- **SQLite объекта — кэш и список незаписанного.** Обёртка `Tracked` над `InMemoryStore`
  замечает, какие туры и версии изменил запрос; объект пишет их в своё хранилище (`t:<id>`,
  порядок списка — `order`) и в список ждущих (`pending`: путь → тур или удаление, со
  счётчиком) **до** ответа. Таймер объекта (alarm) через 30 с пишет всё ждущее одним коммитом —
  5 запросов к GitHub при любом числе файлов; ветку сдвинули — ещё раз поверх. Что пришло во
  время коммита, ждёт следующего (счётчик). Ошибка — в `/api/Info/storage`, повтор через 30 с.
- **Пустой объект поднимается из ветки одним архивом** (`/tarball/<голова>`): по файлу —
  упёрся бы в 50 запросов наружу бесплатного тарифа. 126 файлов — ≈ 2,3 с на первый запрос.
  Голова запоминается: поднятое из ветки уже записано.
- **Help** показывает «Записано в GitHub» как у сервера: `/api/Info/storage` отдаёт те же поля
  (`kind: GitHub`, `pending`, `lastWritten`, `nextWriteInSeconds`, `lastError`).
- **`POST /seed`** с заголовком `X-Master-Key` — туры из файла вида seed (как читает
  `tc-server import`), добавить или записать поверх.
- **`POST /crash`** с тем же заголовком роняет объект: `ctx.abort()`, а с `?panic` — паника в
  Rust-коде. Так проверяется, что будет, если объект упал между правкой и коммитом.
- **Сервер собирается под wasm32** без правок логики: `clock::now()` вместо
  `SystemTime::now()` (на этой цели паникует; в Worker-е — `Date.now()` из JS),
  `clock::spawn` вместо `tokio::spawn` (`spawn_local`), а то, что слушает, отдаёт файлы и пишет
  лог (рантайм tokio, `tower-http`, `tracing-subscriber`, сервер axum), — зависимости только
  для обычной цели. Обычная сборка — как была, её тесты проходят.
- **Не работает здесь:** push не отправляются (нужен reqwest — под wasm его нет; отправка через
  `fetch` проверена прототипом), подписки на push — только в памяти объекта; `wakeup` не ждёт;
  нет перенаправления текстовых браузеров и заголовков кэша из `main`.
- **Настройки:** секреты `MasterKey`, `AuthPrivateECDSAKey`, `STORE_KEY` — свои у этого
  Worker-а, не прода и не беты; `GITHUB_TOKEN` — токен репозитория данных (`cf-secrets.sh`).
  `GITHUB_REPO`, `GITHUB_BRANCH` — в `wrangler.toml`; `CLIENT_ASSET`, `BUILD_ID`,
  `BUILD_COMMIT` — при выкладке (`cf-deploy.sh`). `STORE_OBJECT` — имя объекта (по умолчанию
  `server`): другое — пустой объект, так проверяется подъём из ветки
  (`cf-deploy.sh worker STORE_OBJECT:fresh`). Объекты `fresh1`, `fresh2` от проверки 12.11
  остались — в них ничего не ждёт.

Процессор (`wrangler tail`, после перезапуска объекта): первый запрос, который загружает 126
туров из хранилища, — 55 мс в объекте; дальше вход, список, тур, версии — 0–6 мс в объекте и
0–6 мс в Worker-е; сохранение (`PATCH`) — 5 мс. Все — `ok`.

## Как собрать и выложить

Нужны Node (`wrangler` 4.155.0 — в `package.json`) и `worker-build` (`cargo install
worker-build --version 0.8.7 --locked`), toolchain как у сервера (`RUSTUP_TOOLCHAIN=1.98.1`),
собранный клиент (`trunk build --release` в `rust/crates/tc-web`).

```
cd cloudflare/worker      # или cloudflare/mongo
npm install
CLOUDFLARE_ACCOUNT_ID=… CLOUDFLARE_API_TOKEN="$(cat <файл>)" npx wrangler deploy
CLOUDFLARE_ACCOUNT_ID=… CLOUDFLARE_API_TOKEN="$(cat <файл>)" npx wrangler tail tc-proto --format json
```

В логе `wrangler tail` у каждого вызова — `cpuTime` и `wallTime` (мс), отдельно у Worker-а
и у объекта. Статика Worker не запускает и в логе не видна.

## Падение между правкой и коммитом, 12.11.2026

Правка тура → объект падает, не дождавшись коммита (он через 30 с) → что с правкой?
Проверка — `/home/ad/tourcalc/cf-crash-check.py <abort|panic|deploy>`: тестовый тур добавлен,
переименован, удалён, после каждого шага объект роняется, и 40 с Worker-у ничего не шлют.
Перезапуск виден по `startTime` в `/api/Info/start` (когда объект собрал сервер).

- **Ничего не теряется.** Во всех трёх случаях, на каждом из трёх шагов: правка — в SQLite
  объекта до ответа на запрос, таймер переживает падение, сам будит новый объект, тот
  поднимает туры из SQLite и коммитит через те же ≈ 30 с после правки. Сразу после подъёма
  тур читается уже изменённым (0,1 с).
- **Перевыкладка** (`wrangler deploy` перезапускает все объекты) — без последствий: коммит в
  срок, следующий запрос — новый объект.
- **Паника:** запрос, в котором она случилась, не получает ответа (клиент ждёт до своего
  таймаута — у браузера это долго); остальные запросы и таймер идут как обычно.
- **`ctx.abort()`:** правка тоже уцелела и закоммичена, но объект после него **≈ 13 мин не
  отвечал**: запросы висели до 6 мин и кончались `internal error`, таймер ждал, перевыкладка
  не помогала; пустой объект под другим именем в это время работал. Ожил сам. Похоже на
  особенность самого `abort()` (настоящие падения — паника, перевыкладка — так себя не вели),
  но если объект когда-нибудь «повиснет» так в жизни, это примерно 10–15 мин простоя.

## Mongo

- **Rust-драйвер под Workers не собирается:** `mongodb` 3 тянет tokio с сетью, а `mio`
  отказывается: «This wasm target is unsupported by mio». Значит, Mongo из Rust-Worker-а —
  только через JS: драйвер на JS, а Rust зовёт его через wasm-bindgen.
- **JS-драйвер работает:** подключился к кластеру прода (MongoDB 8.0, три узла, SRV через
  DNS Workers), `hello` отвечен. Atlas пускает адреса Cloudflare — список доступа открыт.
- **Но каждое подключение — 20–24 мс процессора и ≈ 300 мс** (TLS к узлам, обнаружение
  набора реплик) **ещё до входа**; вход (SCRAM-SHA-256) добавит своё. Worker не держит
  соединение между запросами, так что это — на каждый запрос, вдвое больше 10 мс бесплатного
  тарифа. Держать соединение может объект (пока жив), но и он засыпает.
- **Вход и чтение не проверены:** нужен пользователь Atlas — лучше отдельный, только на
  чтение — и его пароль через secret-drop.

## Что из этого следует

- **Код переносится.** `tc-core`, шифрование хранилища и push собрались под Workers без
  правок. Переделывается только среда: `tokio`/`reqwest`/`axum`/диск → `fetch`, Router,
  хранилище объекта, alarm.
- **Всё тяжёлое — в объекте**, Worker только передаёт запрос. Объект и так нужен: один
  писатель с памятью и коммитом по таймеру. Тогда 10 мс Worker-а не встречаются, а у объекта —
  до 30 с на запрос; самое тяжёлое из замеренного (50 push) — 0,3 с.
- **Хранилище GitHub подходит Workers лучше Mongo:** HTTP-запросы, а не соединения;
  коммит — 5 запросов из 50 разрешённых. Mongo возможна, но через JS и с ≈ 20+ мс и 300 мс на
  запрос.
- **Клиент — статикой Workers:** бесплатно, вне лимита запросов, Worker не запускается.
- **Не проверено:** перенос `/t` (≈ 1 800 строк на axum и состоянии сервера — разделить
  разметку и обработчики; процессор — как у балансов), вход в Mongo, сколько живёт прогретый
  объект и сколько стоит его пробуждение, отправка настоящих push (подписки беты), вход и
  права (`auth.rs`), подписки на push в хранилище.
