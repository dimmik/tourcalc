## 1. Доступ и ключи (сервер)

### 1.1 **[высокая]** Ключ подписи токенов по умолчанию — из репозитория

`config.rs`: если `AuthPrivateECDSAKey` не задан, сервер берёт dev-ключ из `appsettings.json`
— тот самый, что лежит в публичном репозитории. Комментарий в коде это признаёт («the app
refuses to start without one if this default is removed»).

Почему плохо: деплой, в котором переменную забыли или опечатали, молча подписывает токены
ключом, который знает любой читатель GitHub. Такой токен с `IsMaster: true` даёт полный доступ
ко всем турам. Ошибка не проявляется ничем — всё работает.

→ Для `BUILD_TYPE` prod/beta отказываться стартовать без ключа (как уже сделано для
`StorageType=MongoDb` без фичи `mongo`). Для `na` (локальная сборка) оставить dev-ключ, но
писать `warn!` при старте. **[по коду]**

### 1.2 **[средняя]** Просроченный или битый токен неотличим от «никто»

`api/mod.rs::Bearer`: токен, который не прошёл проверку (просрочен — по умолчанию через 180
дней — или подписан другим ключом после смены ключа на сервере), превращается в
`AuthData::default()` без ошибки. Дальше `all_suggested` отвечает пустым списком, `Tour/{id}` —
404. Клиент (`api.rs::signed_in`) считает себя залогиненным, пока в localStorage лежит хоть
что-то, и показывает пустой «Your tours» или «This tour is gone, or the login no longer
covers it».

Почему плохо: человек видит «туров нет», а не «войдите заново». После смены ключа сервера так
будет у всех разом.

→ Когда заголовок `Authorization` есть, но токен не принят, — отвечать 401 с причиной
(`expired` / `signature`). В клиенте по 401 — стирать токен и показывать вход. Для текстовых
страниц то же самое через редирект на `/t/login`. **[по коду]**

### 1.3 **[низкая]** `…/{md5}/md5` не приводит хэш к верхнему регистру

`api/auth.rs::token` с `already_md5` берёт строку как есть; текстовый `goto` делает
`to_uppercase()`. Share-ссылка с md5 в нижнем регистре даёт токен, который не совпадёт с
`AccessCodeMD5` в базе (там всегда верхний).

→ `to_uppercase()` и в API. **[по коду]**

### 1.4 **[низкая]** `/api/Info/wakeup/secCode` — публичное удержание соединения

Код по умолчанию `secCode` известен из исходников; каждый вызов держит задачу
`WaketimePreDelayInMin + WaketimePostDelayInMin` минут. Дёшево, но не ограничено.

→ Либо не иметь дефолта (пустой код = ручка выключена), либо лимит одновременных ожиданий.

### 1.5 **[низкая]** `/api/Log/logs`: «Administrators only, like the original» — не проверяется

`let _ = auth.is_master;` — проверки нет. Ответ всегда пустой, поэтому утечки нет, но
комментарий врёт.

→ Либо проверить, либо убрать фразу.

## 2. Целостность данных (сервер)

### 2.1 **[высокая]** PATCH с `IsVersion: true` превращает живой тур в «версию»

`api/write.rs::update`: `IsVersion` из тела принудительно сбрасывается только в ветке
`restoring` (тело — версия с другим id). Если клиент пришлёт **тот же id** и `IsVersion: true`
(ошибка клиента, кривой импорт JSON, ручной запрос), сохранение проходит соft-lock и
записывается как есть.

Почему плохо: тур пропадает из списка (`list` фильтрует версии) и становится нередактируемым
(`version_editable = false` → 403). Вернуть можно только руками в базе.

→ На обычном сохранении принудительно `IsVersion = false`, `VersionFor_Id` убрать —
симметрично тому, что уже делает `add`. Тест на это.

**[проверено]** на in-memory сервере: PATCH `zscph2y` с `IsVersion: true` → `200 OK`;
следующее сохранение того же тура → `403 Forbidden: Versions are not editable`. Пропадание
из списка — по коду (`list` фильтрует `is_version`).

### 2.2 **[средняя]** У администратора клонирование и восстановление версии кладут тур не в ту кучу

`api/write.rs::add`: для мастера код берётся из пути и хэшируется: `code_md5(&code)`.
Клиент (`list.rs::clone`) передаёт `""` → `add_tour(body, "")` подставляет `"-"` → тур
уходит в кучу `md5("-")`. Восстановление версии (`dialogs.rs::VersionsDialog`) передаёт уже
готовый md5 из `AccessCodeMD5` → сервер хэширует хэш → куча `md5(md5)`.

Для обычного кода это не проявляется: сервер игнорирует путь и берёт код из токена. Для
мастера — тур «исчезает» сразу после создания.

→ На сервере: пустой код или `-` у мастера → 400. В клиенте: при клонировании и
восстановлении передавать `AccessCodeMD5` исходного тура, а на сервере принимать
`/api/Tour/add/{code}/md5` по аналогии с токеном.

**[проверено]**: `POST /api/Tour/add/-` мастером → тур с
`AccessCodeMD5 = 336D5EBC…` (это `md5("-")`); токену исходного кода он отвечает 404.
Восстановление с двойным хэшем — по коду, механизм тот же.

### 2.3 **[средняя]** Сервер не проверяет содержимое тура

Ни `add`, ни `update` не смотрят внутрь: пустые или повторяющиеся id участников, трата с
`FromGuid` несуществующего человека, отрицательный вес, пустое имя тура — всё пишется.
Клиенты это проверяют у себя, но API открыт любому с токеном, а `Tour::from_json` уже
однажды пришлось учить чинить дубли id трат на лету (`give_every_spending_its_own_id`) — это
симптом того, что вход не проверяется.

→ Минимальная проверка на сервере с 400: непустые уникальные id людей и трат, `weight > 0`,
`FromGuid` и `ToGuid` указывают на людей тура. Логировать, если пришлось что-то чинить при
чтении.

### 2.4 **[низкая]** `StateGUID` пишется не в том формате, что C#

`new_state_guid()` даёт `"2026-09-18 10:00:00 .a1b2…"` (пробел перед точкой, 32 hex без
дефисов). C#: `"2026-09-18 10:00:00.{Guid}"`. Комментарий обещает «indistinguishable».
Ничто это не парсит, только сравнивает — но при взгляде в базу видно, кто писал.

→ Убрать пробел, писать GUID с дефисами (`new_version_id()` уже умеет).

### 2.5 **[низкая]** Версия пишется после тура без транзакции

Документировано в `mongo.rs::replace`. Потеря записи истории при падении между двумя
записями. Приемлемо; отметить в GUIDE как известное.

### 2.6 **[низкая]** `add` и `delete` читают все туры кода целиком, чтобы их посчитать

`state.store.list(...)` тянет из Mongo каждый тур со всеми тратами ради `mine.len()`.

→ `count_documents` с тем же фильтром (в trait — `count(codes)`).

### 2.7 **[низкая]** Текстовые страницы не шлют push-уведомления

`text/pages.rs::save` пишет версию, но не вызывает `state.announce`. Правка через `/t`
никого не уведомит, а открытый в приложении тур узнает о ней только по `/state`.

→ Вызвать `announce` там же, где в `api/write.rs`.

## 3. Ядро и правки

### 3.1 **[средняя]** Удаление участника тихо удаляет его траты и меняет чужие

`edit.rs::remove_person` (и его копия `text/pages.rs::without_person`):
- все траты, которые он оплатил, **удаляются** — деньги, которые реально были потрачены,
  исчезают из тура;
- трата «только на него» (например, его личная покупка, оплаченная другим) становится
  **«на всех»** — `to.retain` опустошает список и код подставляет `Everyone`.

Подтверждение — «Delete 'Вася'?», ни слова про траты.

→ Как минимум сказать в подтверждении, что уйдёт («…and the 5 expenses he paid for»).
Лучше — не удалять, а запрещать удаление, пока на человеке есть траты (или предлагать
переназначить плательщика). Трату «только на него» логичнее удалять, чем раздавать всем.
Логику вынести в `tc-core` в одном экземпляре. **[по коду]**

### 3.2 **[низкая]** `Tour::from_json` меняет данные при чтении

Переименование повторяющихся id трат при парсинге — нужная починка, но это побочный эффект в
месте, где его не ждут: тест «round trip не меняет тур» теперь верен только для туров без
дублей, и первое же сохранение из Rust записывает новые id в базу, которую читает и C#.

→ Оставить, но логировать факт (сервер) и покрыть тестом, что C#-клиент после этого
открывает тур (проверить на бете на реальном туре `2lv33uy`).

### 3.3 **[низкая]** `Cents` без проверок переполнения

`Add`/`Sub`/`Sum` на `i64` — при абсурдном вводе (`AmountInCents: 9e18`) паника в release
(`overflow-checks` выключены → тихое переполнение). См. 2.3: проверка входа закроет и это.

## 4. Клиент: офлайн и синхронизация

### 4.1 **[средняя]** Очередь, которую нельзя отправить, повторяется вечно

`main.rs::send_what_is_waiting` каждые 20 с и по событиям пытается отправить каждую очередь.
Если тур удалён, токен его больше не покрывает (1.2), или сервер отвечает 400 —
`sync::push` возвращает `Failed`, очередь остаётся, попытки идут до конца времён. Пометка
«2 not sent yet» висит в списке навсегда, выбросить правки нечем.

→ Считать неудачи; после N окончательных (404/400/403) ответов — перестать пробовать и
показать в туре «эти правки не приняты: …» с кнопкой «Discard». Сетевые ошибки продолжать
повторять. **[по коду]**

### 4.2 **[средняя]** Повтор очереди воскрешает удалённое другими

`edit.rs::put_spending` / `put_person`: операция `Put…` с id, которого в туре уже нет,
**добавляет** запись заново. Сценарий: я в офлайне правлю трату, коллега её тем временем
удаляет, у меня появляется сеть — трата возвращается в тур. То же для участников. Комментарий
в коде объясняет это защитой от двойного добавления, но не различает «ещё не добавлено» и
«уже удалено».

→ Хранить в `PutSpending` флаг `is_new`; для правки существующей записи — если id не найден,
пропускать операцию и сказать об этом («“Такси” was deleted by somebody else, your edit was
dropped»). **[по коду]**

### 4.3 **[низкая]** Два лишних запроса на каждое сохранение

`tour.rs::apply` → `sync::record` (PATCH, затем GET для чтения назад) → `reload.run(false)`
→ `sync::push` без очереди → ещё один GET того же тура. Три запроса вместо одного-двух.

→ `record` уже возвращает свежий тур; `apply` может поставить его в state сам, без второго
`load`.

### 4.4 **[низкая]** Список туров: 50 и ни одним больше

`api.rs::tours` просит `from=0&count=50` и не листает. Для обычного кода это не проблема;
администратор с сотнями туров увидит первые 50 без предупреждения.

→ Либо `count=1000`, либо догружать страницы. Заодно показать «показано 50 из N».

### 4.5 **[низкая]** Кэш туров в localStorage не чистится

`__tcw_tour_*`, `__tcw_tour_at_*` для удалённых и чужих туров остаются. Не критично (5 МБ
хватит надолго), но при выходе из аккаунта (`log_out`) чистится только список, а не туры и
очереди — следующий человек на этом устройстве под другим кодом увидит чужой тур из кэша,
если знает id.

→ В `log_out` удалять все ключи с префиксом `__tcw_`.

### 4.6 **[низкая]** «✓ server has nothing newer» по отпечатку, а не по `StateGUID`

`tour.rs::fingerprint` — имя, число людей, число трат, сумма, длительность, флаги, валюта.
Правка описания, плательщика или даты внутри траты отпечаток не меняет → кнопка ↻ честно
покажет «nothing newer», хотя данные пришли другие (тот же дефект, что у Blazor в
`review_3.md` 1.2). У сервера есть `StateGUID`, он и должен решать.

→ Сравнивать `StateGUID` до и после.

## 5. Service worker и PWA

### 5.1 **[средняя]** Кэш `tcw-v1` копит старые сборки навсегда

`sw.js` кладёт каждый `tc-web-<hash>_bg.wasm` (≈1 МБ) в кэш и никогда не удаляет: имя с
хэшем, значит, «всегда верный ответ». После 30 деплоев — 30 МБ мёртвого wasm в браузере
каждого, кто заходил. На телефоне браузер начнёт выкидывать кэш сам, и первым — ненужное
вперемешку с нужным.

→ После успешной навигации (новый `index.html` получен) — вычистить из кэша хэшированные
файлы, которых нет в текущей странице. Или версионировать имя кэша сборкой и удалять старые
в `activate`.

### 5.2 **[средняя]** Текстовые страницы попадают в кэш приложения

Обработчик `navigate` кэширует ответ любой навигации под ключом `/`. Открыл `/t/abc` в том же
браузере — офлайн-заглушкой приложения станет HTML текстовой страницы. И наоборот, `/t/...`
при потере сети ответит приложением.

→ Исключить `/t` и `/t/` из обработчика, как уже исключён `/api/`.

### 5.3 **[низкая]** Два манифеста и `related_applications` на самого себя

`manifest.json` и `manifest.webmanifest` лежат рядом; в `related_applications` перечислены оба
как «webapp». Браузеры это игнорируют, но два файла — два места для правки.

→ Оставить один; второй отдавать редиректом, если старые установки его помнят.

### 5.4 **[низкая]** Кнопка «Update» и push-подписка — решено, но стоит записать

Кнопка больше не снимает регистрацию воркера (иначе терялась подписка). Об этом нет ни
слова в GUIDE в разделе «Грабли», а наступить туда легко снова.

## 6. Наблюдение за чужими правками

### 6.1 **[низкая]** Страница тура не узнаёт, что тур удалили

`others.rs::look`: ошибка `/state` (в том числе 404) — молчаливый `return`. Тур, удалённый
коллегой, остаётся на экране «from server · 3 min ago» до следующей правки, которая упрётся в
404 и попадёт в 4.1.

→ 404 от `/state` → строка «This tour was deleted» и ссылка в список.

### 6.2 **[низкая]** Интервал и «only when I come back» не переживают смену настроек в открытом туре

Настройка читается при открытии страницы (документировано). Мелочь, но подпись в Settings
обещает «applies to the next tour you open», а переключение Full/Mini тоже пересоздаёт
страницу — то есть «применится» непредсказуемо для читателя.

→ Читать сигнал настройки и пересоздавать таймер.

## 7. Сборка, тесты, устройство кода

### 7.1 **[средняя]** `panic = "abort"` действует и на сервер

`rust/Cargo.toml`: профиль `release` для всего воркспейса — `panic = "abort"`, потому что
«a panic in a browser is fatal anyway». Сервер собирается тем же профилем. Значит, любая
паника в обработчике (`expect("store lock")` в `store.rs`, `expect("just listed")` в
`mongo.rs`, индексация в `calc.rs`) убивает **процесс**, а не запрос; axum перехватить
её не может. Podman перезапустит контейнер, но все запросы в полёте и все таймеры ожидания
(`wakeup`) пропадут.

→ Отдельный профиль для сервера (`[profile.release.package.tc-server] panic = "unwind"`
не работает для `panic`; нужен `[profile.server]` и `--profile server` в Dockerfile) и
`CatchPanicLayer` из tower-http. **[по коду]**

### 7.2 **[средняя]** Mongo-тесты не гоняются в CI

`docker-publish-rust.yml`: `cargo test --locked --workspace` без `TC_TEST_MONGO` — 11
тестов слоя Mongo молча пропускаются. Это единственное место, где проверяется формат
документов, совместимый с C#. Проверяется только локально и только когда кто-то вспомнил.

→ `services: mongo:7` в job и `TC_TEST_MONGO=mongodb://localhost:27017`.

### 7.3 **[средняя]** Клиент собирается из CSS Blazor-проекта

`tourcalc.rust.docker` копирует `TCBlazor/Client/wwwroot/css/` в сборку клиента;
`index.html` инлайнит ещё 29 КБ своих правил поверх. Стили одного интерфейса живут в двух
проектах на двух языках; выпилить Blazor нельзя, не перенеся CSS.

→ Перенести `newui.css`/`mini.css` в `rust/crates/tc-web/css/` (Blazor может ссылаться туда
же, пока жив), инлайн из `index.html` — в тот же файл.

### 7.4 **[низкая]** Три файла больше тысячи строк

`tour.rs` 2343, `text/pages.rs` 1354, `mini.rs` 1328. В `tour.rs` живут страница, вкладки
Expenses/Stats/Balance, строка траты, подробности, свежесть и таблица. Каждая правка вкладки
— диф в одном гигантском файле.

→ `tour/{page,expenses,stats,balance,row}.rs`; `text/{tour,people,spend}.rs`.

### 7.5 **[низкая]** Дублирование

- `remove_person` (`edit.rs`) и `without_person` (`text/pages.rs`) — одна логика дважды;
- `access_code_of` (`api/tour.rs`) и `fields::access_code`;
- `fn storage()` — шесть копий по модулям клиента;
- `new_spending_id()` используется для id людей в текстовых страницах (имя вводит в
  заблуждение).

→ В `tc-core`: `Tour::without_person`; в `tc-web`: один `storage()` в `queue.rs` или новом
`local.rs`.

## 8. Что в порядке

Отмечу, чтобы не переспрашивать в следующем раунде:

- Soft-lock через `StateGUID` в одной операции (`replace` и в памяти, и в Mongo) — правильно.
- Очередь как список намерений с повтором поверх свежего тура — правильная модель;
  один отправитель на тур (`sync::Sending`) закрывает двойную запись.
- Токен совместим с C# (ES256, те же claims), проверено тестами; CORS с зеркалированием
  объяснён.
- Доли и балансы — одна арифметика в `tc-core` для сервера, клиента и текстовых страниц;
  golden-тесты против C#.
- Кэширование: хэшированные файлы `immutable`, остальное `no-cache` — верно, с тестом.
- Graceful shutdown по SIGTERM.
- Push: VAPID + шифрование тестируются без сети; мёртвые подписки удаляются и считаются.
- Уведомление открывает нужный тур и не трогает открытую форму (проверено на этой неделе).
