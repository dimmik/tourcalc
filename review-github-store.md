## Находки

### 1. Неверный ключ: сервер молча стартует пустым и затирает подписки — подтверждено, серьёзно

`open()` файл, который не открывается, пропускает с предупреждением в логе. С чужим
`GitHubStoreKey` не открывается ни один — сервер работает с 0 туров, на Help «записано всё».
Хуже: файл подписок `s` лежит по одному и тому же пути при любом ключе, и первая же подписка
перезаписывает его новым ключом. Проба: подписка под ключом A → запуск с ключом B, одна
подписка → снова ключ A: подписок у тура 0 — старые потеряны навсегда. Туры не затираются (их
пути зависят от ключа), но в репозитории появляются вторые, нечитаемые для правильного ключа.

**Предложение:** не стартовать, если наши файлы есть, а не открылся ни один — «GitHubStoreKey не
тот: N файлов в репозитории, ни один не открывается». Отдельный нечитаемый файл — по-прежнему
предупреждение, но `s`, который не открылся, не перезаписывать (подписки — только в памяти до
исправления). ≈ 5 мин с тестом.

### 2. Лимит GitHub на запись: раз в 10 с — больше, чем разрешено за час; при отказе — без паузы — подтверждено по документации

GitHub: не больше 80 «создающих» запросов в минуту и 500 в час, сюда же идут действия в
веб-интерфейсе. Коммит — это три таких запроса (дерево, коммит, сдвиг ветки), так что 500 в
час — это ≈ 166 коммитов, один в ≈ 22 с. При непрерывной правке раз в 10 с получается 360
коммитов — 1080 запросов в час. Достаточно вечера, когда за столом вносят траты.

На превышение GitHub отвечает 403/429 с `retry-after`; документация велит ждать, а «продолжение
запросов может привести к бану интеграции». Сейчас 403/429 — обычный `Failed`, и через 10 с
сервер пробует снова, не глядя на `retry-after`.

**Предложение:** (а) после ошибки — пауза, растущая вдвое (до нескольких минут), и `retry-after`
/ `x-ratelimit-reset`, если они есть; (б) не больше одного коммита в 30 с: изменения всё равно
лежат на диске и в памяти, а «записано» на Help скажет честно. ≈ 10 мин.

### 3. Изменение, которое GitHub отвергает, держит все остальные — вероятно

`flush()` шлёт все изменения одним коммитом. Если одно из них GitHub не принимает, отказ
получают и все остальные, раз за разом, и следующие встают в ту же очередь. Самый вероятный
случай — удаление файла, которого в ветке уже нет. Так бывает, если ответ на удачный коммит
потерялся (таймаут после `PATCH`) или файл удалили руками. Как GitHub отвечает на
`sha: null` для отсутствующего пути, без настоящего репозитория не проверить; репозиторий в
памяти такое молча принимает.

**Предложение:** после `Moved` (и перед каждой попыткой) выкидывать удаления путей, которых
нет в свежем списке файлов ветки. Проверить на живом репозитории (шаг 7). ≈ 5 мин.

### 4. Пока GitHub недоступен, память всё же растёт — подтверждено чтением

В «Что сделано» (`rust/github-store.md`) записано, что вытеснение на диск не даёт памяти расти,
пока GitHub недоступен. Но `changed` держит **запечатанный текст** каждого незаписанного файла,
и в потолок `GitHubMemoryMB` он не входит. Каждое сохранение тура — ещё и новая версия, новый
файл. За долгий простой там окажется всё, что было сохранено. Тексты сжаты, так что «Урал»
занимает ≈ 50 КБ, но рост ничем не ограничен.

**Предложение:** в `changed` держать только путь и номер (или признак удаления), а текст брать
из кэша на диске в момент коммита — он там уже лежит. И исправить фразу в плане. ≈ 5 мин.

### 5. Число файлов растёт с каждым сохранением; при 100 000 сервер не стартует — чтением

Каждое сохранение оставляет версию — отдельный файл `v/…`. Дерево ветки GitHub отдаёт целиком
только до 100 000 записей (или 7 МБ ответа); больше — `truncated`, и `open()` отказывается
стартовать. Это годы работы, а не дни, но упирается в потолок, а не деградирует. Сжатие истории
(следующий шаг в плане) про коммиты, а не про файлы.

**Предложение:** записать в план рядом со сжатием истории — чистить старые версии (или
складывать версии тура в один файл). Сейчас — ничего.

### 6. Мелочи

- **`status()` обходит весь кэш на диске под блокировкой хранилища** (`dir_size`) — каждое
  открытие Help администратором останавливает все чтения и записи на время обхода тысяч
  файлов. Считать размер вне блокировки (или запоминать при записи). ≈ 2 мин.
- **Текстовый интерфейс `/t` для администратора читает все туры целиком** (`list` → `load` для
  каждого), под той же блокировкой, вытесняя из памяти горячие туры. Обычному читателю — только
  его туры, так что это про администратора. Пока — только записать.
- **`GitHubRepo=memory` принимается и в боевой сборке** — с предупреждением в логе, но туры
  пропадут при перезапуске. Можно отказывать, если `BUILD_TYPE` — prod. ≈ 2 мин.
- **Ответ сервера на Help не обновляется сам:** «следующая запись через 5 с» так и висит до
  «Ask the server again». Можно перезапрашивать раз в несколько секунд, пока `pending > 0`.
- **Что видно в публичном репозитории без ключа:** сколько туров, сколько версий у каждого
  (каталог `v/<тур>/`), примерный размер и когда их правили (время коммитов). Содержимое и имена
  — нет. Это свойство схемы, а не ошибка; стоит сказать в плане явно.
